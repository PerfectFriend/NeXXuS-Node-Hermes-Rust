# Игровой дизайн: Элементарная жизнь

## Геометрия поля

Движок поддерживает ДВЕ геометрии сетки, выбираемые игроком при старте
новой игры (UI ещё не реализован для этого выбора — см. `AGENTS.md`,
раздел "Активная задача"):

### Гекс (по умолчанию, исходная версия)
- Гексагональная сетка, осевые координаты (axial coordinates), flat-top
  гексагоны. У каждой клетки 6 равноправных соседей.
- **Sandbox-режим**: большой правильный гексагон со стороной 30 малых
  клеток (`radius = 29` в осевых координатах, всего 2611 клеток).
  Формула числа клеток: `3·R·(R+1) + 1`, где `R = сторона - 1`.
- **Puzzle-режим**: меньшее поле, `radius = 8` (217 клеток).

### Квадрат (добавлено позже, окружение Мура)
- Обычная квадратная сетка, 8 соседей у каждой клетки, включая 4
  диагональных (классическое окружение Мура, как в оригинальной
  "Жизни" Конвея).
- **Sandbox-режим**: `radius = 14` даёт поле 29×29 = 841 клеток (для
  сопоставимой "стороны" с гексом — но число клеток у квадрата и гекса
  при формально одинаковой "стороне" сильно отличается: `side × side`
  против `3R(R+1)+1`. Это нужно явно показывать в UI при выборе сетки,
  чтобы не создавать у игрока ложное ожидание одинакового масштаба).
- **Puzzle-режим**: `radius = 6` даёт поле 13×13 = 169 клеток
  (сопоставимо с 217 клетками гекс-головоломки).

### Почему числовые пороги разные у двух геометрий

При 8 соседях те же правила статистически срабатывают иначе, чем при 6
— это не теоретическое предположение, а результат headless-тестов.
Прямой перенос гекс-параметров `classic_balanced` (`birthCount=3,
lifeOverpopulation=6`) на квадратную сетку без изменений давал **36%
поля жизнью** против целевых ~15% у гекса — потому что "ровно 3 из
8 соседей" статистически набирается чаще, чем "ровно 3 из 6". После
перекалибровки (`birthCount=4, lifeOverpopulation=7` для
`classic_balanced`) баланс квадрата вышел на сопоставимое с гексом
плато (~16% поля).

Отдельный нетривиальный случай — `desert_drought`: на квадрате
повышение `earthDryoutChance` (быстрое высыхание земли, как у
гекс-версии засухи) парадоксально **увеличивало** популяцию жизни, а не
уменьшало. Причина: высохшая земля становится `empty`, а `empty` легче
"перекомбинируется" в `water+life→earth→life` цикл, чем устоявшаяся
`earth`, которая просто долго ждёт нужной комбинации соседей. Решение:
для квадратной засухи реальный угнетающий фактор — `survMin: 1`
(изолированная жизнь гибнет быстрее), а не агрессивное высыхание земли.
Это пример того, что калибровку нельзя переносить по аналогии "взять то
же самое и пропорционально увеличить" — нужно эмпирически проверять
headless-тестами каждый раз, когда меняется геометрия или правило.

Структура констант в коде: `GEOMETRY_PRESETS.hex` / `GEOMETRY_PRESETS.square`,
`GEOMETRY_LEVELS.hex` / `GEOMETRY_LEVELS.square`, `PUZZLE_RADIUS.hex` /
`PUZZLE_RADIUS.square`. Старые имена `PRESETS`/`LEVELS` оставлены как
алиасы на `.hex`-версии для обратной совместимости с кодом, написанным
до введения мультигеометрии.

## Состояния клетки

| Состояние | Описание |
|---|---|
| `empty` | Пустота (изначальная, нетронутая) |
| `life`  | Живая клетка |
| `fire`  | Огонь (живёт максимум 2 тика без тушения) |
| `water` | Вода |
| `earth` | Земля / берег |
| `steam` | Пар (испарившаяся вода) |
| `ash`   | Пепел (выгоревшая клетка) |

Каждая клетка хранит `{ state, age, wetStreak? }`:
- `age` — сколько тиков подряд клетка находится в текущем состоянии
  (используется для тайминга переходов и для критерия победы в puzzle).
- `wetStreak` — отдельный счётчик у `ash`: сколько тиков подряд рядом
  есть вода (используется только для перехода `ash → earth`, не путать
  с `age`).

## Закон сохранения воды

`total(water) + total(steam) = const`. Это центральный инвариант игры,
озвученный изначально пользователем как жёсткое требование. Вода:
- испаряется в пар, когда тушит огонь (через жизнь или напрямую);
- выпадает дождём (пар → вода) через `steamRainTicks` тиков;
- физически перемещается при "переливе" (см. ниже) — клетка-источник
  становится `earth`, клетка-цель становится `water`;
- в puzzle-режиме розлив игроком создаёт воду "из ничего" с точки зрения
  локального инварианта поля, но концептуально это не нарушение —
  капли воды — отдельный, явно ограниченный ресурс игрока (лимит на
  уровень), который вводится намеренно как механика головоломки.

## Правила переходов (полная логика в `src/engine.js`, функция `stepField`)

### LIFE (жизнь)
- Если рядом есть `fire`:
  - Если рядом есть `water` — клетка спасается (вода тушит огонь,
    испаряясь в пар; жизнь выживает).
  - Если воды нет — огонь **обязательно** перекидывается на эту клетку
    (`life → fire`). Не вероятностно — это сознательное решение по
    итеративному дизайну (см. "История находок").
- **Перенаселение без воды**: если у клетки `≥ lifeOverpopulation`
  соседей-`life`, и при этом нет воды рядом — клетка "перегревается":
  копит счётчик `age` в этом особом состоянии, и после
  `overpopulationIgniteTicks` тиков самовоспламеняется (`life → fire`).
  Это и есть переосмысленное правило "перенаселения" из классической
  Жизни — вместо тупой гибели оно даёт причинно-следственный пожарный
  механизм.
- Если перенаселена, но вода рядом есть — вода "охлаждает" клетку,
  перегрев не накапливается.
- **Молния**: отдельный, явно более редкий случайный источник огня
  (`lightningChance`), не связанный с перенаселением. Без него на
  поле без естественных пожаров система может "замереть" навечно —
  это было обнаружено эмпирически на раннем этапе разработки.
- Изоляция: если соседей-`life` меньше `survMin` — клетка погибает
  в `earth`.

### FIRE (огонь)
- Если рядом есть `water` — гасится, становится `ash`.
- Если прожил `≥ 1` тик без тушения (то есть это второй тик существования)
  — гаснет сам, становится `ash`.
- Иначе горит ещё один тик.

### WATER (вода)
- Если эта вода используется для тушения соседнего `fire`, либо для
  спасения соседней `life`, атакуемой огнём — испаряется в `steam`.
- Если участвует в "переливе" (см. ниже) как источник — становится `earth`.
- Иначе остаётся водой.

### EARTH (земля)
- **Оживление**: если среди соседей есть хотя бы 1 `life`, и сумма
  (`water + life`) среди соседей равна **ровно** `birthCount` (по
  умолчанию 3) — земля оживает (`earth → life`). Это было changed по
  явному запросу пользователя с диапазона на точное число — см. ниже.
- Если воды нет, может самовоспламениться от молнии (с шансом
  `lightningChance × 0.5`, то есть реже, чем у живой клетки).
- **Высыхание**: если воды нет долго (`age ≥ earthDryoutMinAge`), есть
  малый шанс (`earthDryoutChance`) высохнуть в `empty`. Это нужно для
  баланса — без высыхания земля только накапливается, и система
  "затвердевает" без динамики.

### STEAM (пар)
- Выпадает дождём (`steam → water`) через `steamRainTicks` тиков
  (по умолчанию 1).

### ASH (пепел)
- Если рядом и вода, и жизнь одновременно — мгновенно становится
  `earth` ("жизнь распахивает целину" — формулировка пользователя).
- Если эта клетка — цель перелива воды (см. ниже) — становится `water`.
- Если рядом есть вода `wetStreak` тиков подряд (`≥ ashToEarthTicks`,
  по умолчанию 2) — становится `earth`.
- Иначе остаётся пеплом, `age` растёт.

### EMPTY (пустота)
- Если рядом и вода, и жизнь одновременно — мгновенно становится
  `earth` (симметрично правилу `ash`, по требованию пользователя:
  "пустота и пепел — это одно и то же" с точки зрения этого правила).
- Если является целью перелива — становится `water`.
- Если рядом ≥ 2 очага огня — может загореться с шансом `fireSpreadChance`.
- Иначе остаётся пустой, `age` растёт.

### Перелив воды ("острова")
Если клетка `water` полностью окружена 6 соседями-`water`, и у одного
из этих соседей есть соседняя `empty`/`ash` клетка — вода "перетекает":
клетка-источник становится `earth` (берег), клетка-цель становится
`water`. Цель ищется только среди клеток, которые **не** распахиваются
в этот же тик правилом "вода+жизнь рядом" — иначе возникает гонка
(см. "История находок", баг #2).

## Параметры (настраиваемые в UI, фиксированные в пресетах)

| Параметр | Назначение |
|---|---|
| `fireSpreadChance` | Шанс распространения огня в пустоту при ≥2 очагах рядом |
| `overpopulationIgniteTicks` | Тиков до самовоспламенения перенаселённой жизни без воды |
| `lightningChance` | Шанс случайного поджига (не от перенаселения) |
| `survMin` | Минимум соседей-жизни для выживания изолированной клетки |
| `birthCount` | Точная сумма (вода+жизнь) соседей земли для оживления |
| `lifeOverpopulation` | Порог числа соседей-жизни для перегрева |
| `earthDryoutChance` / `earthDryoutMinAge` | Высыхание земли без воды |
| `ashToEarthTicks` | Тиков с водой подряд для перехода пепла в землю |
| `steamRainTicks` | Тиков до выпадения пара дождём |
| `waterOverflowEnabled` | Включён ли перелив воды (острова) |

## 5 пресетов (sandbox)

`classic_balanced`, `fire_storm`, `water_world`, `desert_drought`, `chaos`
— каждый протестирован headless-симуляцией на 2000-3000 тиков:
закон сохранения воды держится без исключений, популяция жизни выходит
на устойчивое (не нулевое, не взрывное) плато.

## Режим головоломки ("Полив пустоты")

Идея пользователя: вся пустота и пепел могут быть "оживлены" простой
заливкой водой. Игроку даётся стартовое поле с ограниченным количеством
воды и лимит капель ("капля" = мгновенное превращение одной клетки
`empty`/`ash` в `water`, тратит 1 из лимита).

- Мир продолжает тикать сам — игрок подливает воду "на лету", не
  останавливая симуляцию.
- **Победа**: пустота/пепел не задерживаются на поле дольше
  `WIN_MAX_AGE` (3) тиков подряд, и это держится стабильно
  `WIN_STABLE_TICKS` (15) тиков. Экосистема может пережить редкую
  молнию — если воды/жизни достаточно, новый пепел не успевает
  "состариться" до победного порога.
- **Поражение**: капли закончились, и долго (80+ тиков) нет победы.
- 5 уровней, плотность изначальной воды убывает (35% → 10%), лимит
  капель растёт (55 → 115) — каждый уровень проверен симуляцией
  "жадного игрока" (см. `docs/` истории чата, если потребуется
  воспроизвести расчёт).

## История находок (важно при рефакторинге/портировании)

При добавлении puzzle-режима были найдены и исправлены два бага в
существовавшей логике — оба актуальны и для sandbox-режима, исправление
применяется одинаково везде:

1. **`age` у `empty`/`ash` сбрасывался в 0 каждый тик** вместо честного
   накопления, если ничего не происходило. Это делало невозможным
   измерение "сколько тиков клетка простояла пустой" — критичная вещь
   для критерия победы puzzle-режима. Исправлено: `age` теперь растёт
   монотонно, пока клетка остаётся в том же состоянии; отдельный
   счётчик `wetStreak` введён специально для тайминга `ash → earth`.

2. **Нарушение закона сохранения воды через "перелив в пепел".**
   Перелив воды искал цель среди `empty` ИЛИ `ash` клеток, но код,
   реально записывающий воду в целевую клетку, проверял
   `overflowTargets.has(k)` только в ветке `case STATE.EMPTY`, а не
   в `case STATE.ASH`. Источник воды добросовестно становился `earth`
   (считая, что перелился), а целевой `ash` воду не получал — она
   просто пропадала. Найдено через headless-тест на 800 тиков с
   заливкой всей пустоты водой (для проверки критерия победы) —
   обычные короткие прогоны (50-100 тиков) баг не показывали.
   Исправлено: ветка `ASH` теперь тоже проверяет `overflowTargets.has(k)`.

**Вывод для будущей разработки**: при любых изменениях логики стихий
обязательно прогонять headless-тест (без UI) на ≥500-1000 тиков и
явно сравнивать `water + steam` на каждом тике, а не доверять
визуальному "вроде работает" на коротком ручном прогоне в браузере.
Баг #2 не проявлялся 5+ итераций разработки именно потому, что короткие
визуальные проверки его не ловили.
