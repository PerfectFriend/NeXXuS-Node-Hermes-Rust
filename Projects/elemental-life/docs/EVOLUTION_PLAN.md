## Фаза 0: Критические баги (сделать сейчас)

### 0.1. `crypto.subtle` недоступен на Android WebView

**Проблема:** Capacitor WebView работает по `file://` — не secure context. `crypto.subtle.digest()` и `crypto.subtle.importKey()` бросают TypeError. Это ломает: регистрацию, разблокировку по seed-фразе, сохранение/загрузку контейнеров. ВСЕ новые пользователи получат белую страницу при попытке создать профиль.

**Решение в порядке предпочтения:**

1. **Best: Упростить identity до минимума.** Убрать BIP39, PIN, panic, контейнеры. Оставить только `localStorage.setItem('profile', JSON.stringify(..))`. Заменить `userInputToEntropy` на простой `SHA-256` через `crypto.subtle` с fallback на полифилл (или на чисто математический хеш без Web Crypto). Игра — клеточный автомат, ей не нужен BIP39, PBKDF2, XOR-шифрование и panic-режимы.

   **Что конкретно убрать:**
   - `bip39.ts` — весь файл, кроме `seedToGameKey` (заменить на простой хеш)
   - `secureContainer.ts` — весь файл, заменить на `saveJSON(key, data)` / `loadJSON(key)`
   - `RegistrationFlow.tsx` — упростить до 1 шага (введите seed → игра)
   - `PinEntryScreen.tsx` — удалить, заменить на кнопку «Играть»
   - Из `useIdentity.ts` убрать seedPhrase, seedHex, PIN-зависимости
   - Из `App.tsx` убрать экраны регистрации/PIN

   **Экономия:** ~1200 строк кода, 22KB из бандла (wordlist BIP39), устранение ~10 багов.

2. **Fallback:** Полифилл для `crypto.subtle` через чистый JS (js-sha256, pbkdf2-hmac в pure JS). Оставит всю текущую архитектуру рабочей, но не исправит переусложнение.

### 0.2. Отсутствует состояние `ash`

**Проблема:** В `GAME_DESIGN.md` описано 7 состояний. В коде — 6. `fire` тушится сразу в `empty` (строки 720-723 `engine.ts`), минуя `ash`. Из-за этого:
- Пепел никогда не появляется
- `wetStreak` (счётчик влажности) на `empty` никогда не растёт
- `ash → earth` через `water+life` или `wetStreak >= 3` никогда не срабатывает
- Экология поля обеднена

**Решение:** Добавить `ASH = 'ash'` в `STATE`, `StateKey`. Изменить `fire`-переходы на `{ state: STATE.ASH, age: 0 }`. Добавить логику для `ash` в `stepField` (wetStreak, water+life → earth). Подкрасить `COLORS.ash` (серо-чёрный, `#2a2a2a`).

**Риск:** Меняет баланс — пепел занимает место, дольше не даёт появиться жизни. Потребуется перекалибровка пресетов.

### 0.3. `birthCount` захардкожен в 3 для earth→life

**Проблема:** Строка 760 `engine.ts` проверяет `sumWL === 3` вместо `params.birthCount`. Для square-геометрии `birthCount = 4`, но используется hex-значение 3. Это означает, что земля→жизнь на квадратной сетке работает с неверным порогом.

**Решение:** `sumWL === params.birthCount`

## Фаза 2: Геймплей (3-5 дней)

### 2.1. Палитра цветов

Текущие цвета функциональны, но не атмосферны. Предлагаю тёмную природную палитру:
- empty: `#0a0e14` (угольный)
- life: `#4ade80` (травяной)
- fire: `#fb923c` (оранжевый, менее агрессивный)
- water: `#38bdf8` (небесно-голубой)
- earth: `#a16207` (золотисто-коричневый)
- steam: `#94a3b8` (серо-голубой)
- ash: `#1e293b` (тёмно-серый, если добавлен)

И анимацию появления/исчезновения через альфа-наложение.

### 2.2. Сохранение состояния игры

- Автосохранение поля каждые 10 тиков в localStorage
- При перезапуске: кнопка «Продолжить» восстанавливает последнее поле
- Отдельные слоты сохранения для sandbox (1 слот) и puzzle (поуровнево)

### 2.3. Информация об элементах при тапе

Долгий тап / тап по информационной кнопке показывает название элемента и правила его взаимодействия. Особенно важно для puzzle-режима, где игрок должен понимать, как вода тушит огонь и питает жизнь.

### 2.4. Простое обучение (onboarding)

При первом запуске 3 экрана:
1. «Коснитесь пустой клетки, чтобы добавить воду»
2. «Запустите симуляцию — вода даст жизнь, жизнь превратит пустоту в землю»
3. «В режиме головоломки расставьте воду так, чтобы не осталось пустоты»

### 2.5. Турнирная таблица puzzle

Локальный учёт времени прохождения каждого уровня (количество тиков до победы). Для каждого уровня — рекорд (минимум тиков) и количество попыток.

## Фаза 3: Производительность (2-3 дня)

### 3.1. Visible rect culling

**Проблема:** `render()` итерирует все 2611 клеток каждый раз, даже если видно только 100. С z-index `board-wrap` выше тулбара, но Canvas всё равно рисует невидимые клетки.

**Решение:** В `GridRenderer.render()` вычислять bounding rect видимой области в мировых координатах и пропускать клетки, целиком находящиеся за его пределами.

### 3.2. Web Worker для stepField

`stepField` — чистая функция без DOM-зависимости. Можно вынести в Web Worker. Это освободит главный поток для React-рендеринга и анимаций.

**Проблема:** Map и функции (rng) не передаются в Worker через `postMessage`. Нужно сериализовать field в плоскую структуру (массив `{key, state, age, ...}`) и десериализовать обратно. Это добавляет latency ~1-2ms на передачу.

### 3.3. virtualScroll для StatsDisplay

При 5 элементах неактуально, но при росте статистики может пригодиться.

## Что НЕ делать (антиприоритеты)

- **Не портировать на React Native** — Capacitor WebView достаточно производителен для Canvas 2611 клеток. RN добавит только накладные расходы на мост JS↔Native.
- **Не добавлять мультиплеер** — синхронизация клеточного автомата между клиентами — нетривиальная Distributed Systems задача без явного запроса.
- **Не добавлять облачную синхронизацию** — без серверной инфраструктуры это будет Firebase или аналог с дополнительными расходами и зависимостями.
- **Не переписывать на Godot** — если только нет цели выйти на Steam/консоли. Capacitor покрывает Android + iOS + Web одним кодом.
- **Не добавлять новые стихии** (metal, crystal, void) — 6 (+ ash) стихий дают 30 парных взаимодействий, что уже сложно для восприятия. Добавление новых экспоненциально увеличивает сложность правил.
