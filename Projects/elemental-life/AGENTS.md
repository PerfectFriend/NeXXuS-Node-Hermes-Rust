# AGENTS.md — инструкции для AI-агента (opencode)

Этот файл читается агентом opencode автоматически при запуске в этой
директории. Здесь — рабочий контекст и конкретное задание.

---

## ⚠️ ОБНОВЛЕНИЕ: `src/engine.js` изменился — изменилась сигнатура API

**Если ты уже начал работу по этому AGENTS.md в предыдущем заходе** —
прочитай этот раздел перед тем, как продолжать. Движок `src/engine.js`
расширен: теперь он поддерживает **две геометрии сетки** — гекс (6
соседей, было изначально) и квадрат (8 соседей, окружение Мура,
добавлено по запросу пользователя). Это **breaking change** в сигнатурах
функций движка — если ты уже написал UI-код, вызывающий старые сигнатуры,
его нужно обновить, иначе сборка не заработает.

### Что изменилось в API (старое → новое)

| Было | Стало |
|---|---|
| `buildInitialField(radius, seed)` | `buildInitialField(geometryKey, radius, seed)` |
| `stepField(field, radius, params, rng)` | `stepField(geometryKey, field, radius, params, rng)` |
| `buildLevelField(radius, seed, level)` | `buildLevelField(geometryKey, radius, seed, level)` |
| `neighborsOf(q, r)` | `neighborsOf(geometryKey, q, r)` |
| `makeHexagonalGrid(radius)` (единственная сетка) | `makeGrid(geometryKey, radius)` (универсальная) — `makeHexagonalGrid`/`makeSquareGrid` остались как геометрия-специфичные реализации внутри |
| `hexGridCellCount(side)` (единственная) | `gridCellCount(geometryKey, side)` (универсальная) — `hexGridCellCount`/`squareGridCellCount` остались внутри |
| `PRESETS` (только гекс) | `GEOMETRY_PRESETS.hex` / `GEOMETRY_PRESETS.square`. `PRESETS` оставлен как алиас на `.hex` для совместимости, но **используй `GEOMETRY_PRESETS[geometryKey]`**, чтобы поддержать обе геометрии |
| `LEVELS` (только гекс) | `GEOMETRY_LEVELS.hex` / `GEOMETRY_LEVELS.square`. Аналогично, `LEVELS` — алиас на `.hex` |
| `PUZZLE_RADIUS` (число, только гекс) | `PUZZLE_RADIUS.hex` / `PUZZLE_RADIUS.square` (объект, не число!) |
| `DIRS` (массив, только гекс) | `HEX_DIRS` / `SQUARE_DIRS` (раздельные именованные массивы) |

`geometryKey` — это строка `"hex"` или `"square"`. Передаётся явно во
все вызовы, которые работают с конкретным полем — это выбор пользователя
при старте новой игры (см. новую задачу ниже).

### Новая задача: переключатель геометрии в UI

Добавь в UI экран/диалог "Новая игра" с выбором геометрии сетки
(`hex` или `square`) — по смыслу, как выбор пресета, только это выбор
делается **один раз при старте новой игры**, а не меняется на лету
(смена геометрии меняет структуру `field`/`Map`, поэтому требует полного
пересоздания поля — это нормально, как и смена уровня в puzzle-режиме).

- В sandbox-режиме: после выбора геометрии — обычный выбор пресета
  из `GEOMETRY_PRESETS[geometryKey]` (5 пресетов на каждую геометрию,
  одинаковые по названиям/описаниям, разные числовые params внутри —
  пользователю не нужно видеть разницу в числах, только в поведении).
- В puzzle-режиме: уровни берутся из `GEOMETRY_LEVELS[geometryKey]`,
  радиус поля — из `PUZZLE_RADIUS[geometryKey]`.
- **Важно для UX**: у гекса и квадрата разное число клеток при
  формально одинаковой "стороне" (см. `docs/GAME_DESIGN.md`, раздел
  "Геометрия поля" — там объяснено почему и приведены точные числа).
  Если в UI показывается размер поля — показывай реальное число клеток,
  а не "сторону", чтобы не создавать ложного ожидания одинакового
  масштаба между двумя геометриями.
- Рендер квадратной сетки на Canvas — обычные квадраты/прямоугольники,
  это даже проще, чем гекс-полигоны, которые ты уже, вероятно, реализовал.

Прогони `node tests/engine.smoke.test.mjs` после интеграции — он уже
обновлён и проверяет обе геометрии (10 пресетов суммарно), должен
проходить полностью.

## Контекст проекта

"Элементарная жизнь" — гексагональный клеточный автомат (расширение
"Жизни" Конвея четырьмя стихиями: огонь, вода, воздух, земля), с
песочницей и режимом головоломки. Прототип был разработан в чате с
Claude (Anthropic) как React-артефакт. Полная история дизайнерских
решений и найденных багов — в `docs/GAME_DESIGN.md`. **Прочитай этот
файл первым**, прежде чем трогать любой код — там объяснено, почему
правила именно такие, и описаны два уже найденных и исправленных бага,
которые легко случайно вернуть при рефакторинге.

Игровое ядро уже отделено от UI: `src/engine.js` — чистый ES-модуль без
React/DOM-зависимостей, проверенный `tests/engine.smoke.test.mjs`.
Референсная реализация интерфейса (как это выглядело и работало в
Claude Artifacts) — `reference/ElementalLife.reference.jsx`. Она НЕ
запускается как обычный React-проект без адаптации (специфичный рантайм
Claude Artifacts — нет npm, своя система сборки) — используй её как
референс поведения UI, а не как стартовый код для прямого запуска.

## Твоя задача

Превратить этот прототип в реальный, собираемый Android-проект на базе
**Capacitor**, сохранив игровую логику из `src/engine.js` без
функциональных изменений. Подробный план — `docs/PORTING_PLAN.md`,
прочитай его перед началом работы.

### Конкретные шаги (выполняй по порядку, не пропускай проверки):

1. **Инициализируй Capacitor-проект** с Vite + React в корне репозитория
   (или в подпапке `app/`, если так удобнее организовать монорепо —
   на твой выбор, но опиши решение в комментарии к коммиту).

2. **Перенеси `src/engine.js` в новый проект без изменений логики.**
   Сразу после переноса прогони эквивалент `tests/engine.smoke.test.mjs`
   в новом окружении — закон сохранения воды (`water + steam = const`)
   должен держаться на ≥500 тиках по всем 5 пресетам. Если не держится —
   это значит ты что-то задел при переносе, остановись и разберись,
   прежде чем продолжать (см. "История находок" в `GAME_DESIGN.md` —
   там описаны похожие баги и как их искали).

3. **Построй UI слой заново на Canvas** (не SVG — на полноразмерном
   sandbox-поле 2611 клеток SVG-рендер через тысячи DOM-нод не
   масштабируется на мобильные устройства). Ориентируйся на
   `reference/ElementalLife.reference.jsx` для:
   - списка экранов/вкладок (Пресеты, Настройка, График, Правила)
   - механики режима головоломки (счётчик капель, оверлей победы/поражения,
     полоса прогресса стабильности)
   - переключателя режимов (Песочница / Головоломка)
   Не обязательно копировать вёрстку 1:1 — адаптируй под мобильные паттерны
   (например, вкладки нижним таб-баром вместо боковой панели).

4. **Реализуй жесты** зума и панорамирования поля через нативные touch-события
   или библиотеку жестов на твой выбор — главное, чтобы пинч-зум и
   перетаскивание работали плавно на реальном (не эмулированном) устройстве.

5. **Профилируй `stepField`** на полноразмерном sandbox-поле на
   рил-девайсе или хотя бы реалистичном эмуляторе среднего класса
   (не топовый). Если тик занимает больше ~50мс стабильно — оптимизируй
   (см. варианты в `PORTING_PLAN.md`: реже считать overflow, или перенести
   расчёт в Web Worker).

6. **Собери Android-сборку** (`npx cap add android`, `npx cap sync`),
   убедись, что проект открывается и собирается в Android Studio без
   ошибок. Не обязательно подписывать релизный APK/AAB — debug-сборки
   достаточно для проверки на этом этапе.

7. **Пройди вручную все 5 уровней головоломки** на собранном APK (на
   эмуляторе или устройстве), чтобы подтвердить, что баланс уровней
   (см. таблицу в `GAME_DESIGN.md`, раздел "Режим головоломки")
   по-прежнему работает на мобильном экране — лимиты капель не должны
   ощущаться как "слишком жёстко" или "слишком легко" при реальном клике
   пальцем (а не идеальной кликом мыши, как при первоначальной калибровке).

### Что нельзя менять без явного запроса пользователя

- Формулы и пороги игровой логики в `src/engine.js` (правила переходов
  между стихиями, параметры пресетов в `GEOMETRY_PRESETS`, лимиты капель
  в `GEOMETRY_LEVELS`) — это всё откалибровано headless-тестами
  отдельно для каждой геометрии, рефакторинг кода — да, изменение
  чисел/правил — нет, если не попросили явно.
- Критерий победы головоломки (`WIN_MAX_AGE`, `WIN_STABLE_TICKS`) —
  формулировка "пустота не должна жить дольше N тиков, держится M тиков
  подряд" — это прямой пользовательский запрос с обоснованием
  ("за 3 года жизнь и вода навели порядок").

### Что можно и нужно менять свободно

- Любая организация файлов, структура компонентов, выбор библиотек
  рендеринга/жестов/сборки — это твоя инженерная зона ответственности.
- Визуальный дизайн, если он не противоречит смыслу референса (стихии
  должны визуально отличаться по цвету, как в `COLORS` в `engine.js`,
  но конкретная палитра/анимации — на твой вкус).

## Когда задача считается выполненной

- [ ] `engine.js` перенесён без изменений логики, смоук-тест проходит
      (10 пресетов: 5 hex + 5 square)
- [ ] UI поддерживает выбор геометрии (hex/square) при старте новой игры
- [ ] Android-проект собирается в Android Studio без ошибок
- [ ] Оба режима (песочница, головоломка) работают на эмуляторе/устройстве
      для ОБЕИХ геометрий
- [ ] Зум и панорамирование работают плавно через тач на обеих геометриях
- [ ] Все 5 уровней головоломки пройдены вручную хотя бы раз для каждой
      геометрии (10 прохождений суммарно)
- [ ] Краткий отчёт о проделанной работе и оставшихся проблемах
      (если есть) — в виде нового файла `docs/PORTING_REPORT.md`

Если в процессе возникнут неоднозначности, которые меняют игровой баланс
или поведение, описанное в `GAME_DESIGN.md` — задокументируй решение в
`docs/PORTING_REPORT.md`, а не молчи о нём.
