## 3. Новые конспекты (все — в `knowledge-base/`, со связями `[[...]]`)

### 3.1 `NVIDIA-SkillEvaluator-Tiers-2026.md` (laya 1.5734)
Источники: `github.com/NVIDIA/SkillEvaluator`, `docs.nvidia.com/skills/skillevaluator/`, arXiv:2608.20614.

Три независимых уровня, каждый отвечает на свой вопрос:
- **Tier 1 Validation** — безопасен и корректен? Детерминированные schema/quality/security/PII/license/script-проверки офлайн + опциональный LLM-as-judge. Ключ не нужен.
- **Tier 2 Deduplication** — не дублирует? Embedding-сходство внутри скилла и по каталогу.
- **Tier 3 Live Evaluation** — реально помогает? Живой агент выполняет сгенерированные задачи **с** и **без** скилла в песочнице; измеряется **Skill Lift** (разница) + **pass@k** + 5 осей (Security, Correctness, Discoverability, Effectiveness, Efficiency).

Гейты: Tier 1 всегда блокирует `validate`; Tier 2 блокирует по умолчанию (`--no-block-on-dedup` → advisory); Tier 3 advisory по умолчанию (`--block-on-agent-eval` → гейт). Есть recipe для GitHub Actions. **Support level: Experimental**, без SLA.
**Для Живого Кода:** у нас ~880+ скиллов; `quality-check` (Tier 1) — бесплатный офлайн-гейт по всем скиллам; Tier 2 — уборка дублирующих инструкций из общего SYSTEM; Tier 3 — первая честная метрика «помогает ли скилл», которой у нас нет.

### 3.2 `Rogue-Agent-Evaluator-RedTeam-2026.md` (laya 1.6162)
Источник: `github.com/rogue-security/rogue` (Apache-2.0, 225 коммитов).

Два режима: **Automatic Evaluation** (сценарии + ожидаемые исходы, проверка бизнес-политик, pass/fail с рассуждением, смотрит живые диалоги) и **Red Teaming** (75+ уязвимостей в 12 категориях, 20 техник атак — encoding/social engineering/injection, **CVSS-скоринг**, 8 комплаенс-фреймворков: OWASP, MITRE, NIST, GDPR, EU AI Act).
**Для Живого Кода:** готовый формат регрессии роя «сценарий → ожидаемый исход → pass/fail»; red team ловит prompt-injection против агентов с shell/файлами/Telegram, чего обычные тесты не видят. Ограничение: читать `IMPLEMENTATION_STATUS.md` — заявленное ≠ реализованное; агенту надо быть доступен как сервис.

### 3.3 `A2A-v1-MCP-Division-2026.md` (laya 1.2603)
Источники: спецификация A2A v1.0.0 (Приложение B) и `a2a-protocol.org/latest/topics/a2a-and-mcp/`.

Канон из спецификации: **MCP — вертикаль** (углубляет одного агента: каждое MCP-соединение даёт ещё один инструмент, всё под одной крышей), **A2A — горизонталь** (пересекает границу: другой агент может быть другой команды/партнёра). Различие по природе объекта: MCP — примитивы с чётким входом/выходом, часто stateless; A2A — автономные системы с состоянием, планированием и многоходовыми диалогами. Схема: `User ─A2A→ Agent A ─A2A→ Agent B ─MCP→ Tools`.
Нюанс: A2A-сервер может отдавать навыки как MCP-ресурсы (для stateless tool-подобных), но сила A2A — в stateful-партнёрстве. **Для Живого Кода:** MCP — наш основной рабочий слой; A2A нужен для делегирования соседу, когда агенты станут отдельными сервисами; opaque execution — правильная семантика (не отдавать внутренние планы).
