## 5. Новая находка (Laya-триаж)

### Н-1. Миграция схемы БД v1→v2 не реализована — `index build --force` и `index update` падают `OperationalError`

**Суть.** `init_schema()` объявляет в докстринге «создать схему, если её нет; **мигрировать при необходимости**», но миграции нет: используется только `CREATE TABLE IF NOT EXISTS`, который не добавляет колонки в уже существующие таблицы. При этом `SCHEMA_VERSION` поднят с 1 до 2, а новая схема добавляет колонки `records.ord`, `records.payload` и `cycles.duplicates_count`, `cycles.file_sha256`.

**Воспроизведение (изолированная копия корпуса, рабочая БД не тронута):**
```
v1-БД создана вручную (схема коммита a492a8a, SCHEMA_VERSION=1)
load_index(v1)        -> None            (корректно: версия не та)
index_exists(v1)      -> False
build_index(force=True)-> OperationalError: table records has no column named ord
update_index(v1)      -> OperationalError: no such column: file_sha256
```
Обе команды в `cli.py` (строки 774, 800) не оборачивают вызов в `try/except` — пользователь получает сырое исключение с трассировкой вместо внятного сообщения.

**Почему это не «ложная тревога»:** прошлая версия индекса (`a492a8a`, `SCHEMA_VERSION = 1`) — реальный предшественник в истории этого же репозитория; схема v1 → v2 — это не гипотетика, а штатный апгрейд существующей установки. При этом `build_index` не удаляет старый файл БД, поэтому даже после починки схемы данные v1 останутся в том же файле.

**Критичность:** средняя. Канон на диске не повреждён, `corpus()` при негодном индексе корректно падает обратно на дисковое чтение, данные целы. Но индекс не пересобирается — то есть основная цель модуля (ускорение) недостижима ровно у тех, кто обновляет установку, а ломается неочевидно.

**Влияние на живое окружение: нулевое.** БД `memory/corpus.db` в `.gitignore` (артефакт, а не репозиторий), живая БД уже пересобрана кодером в v2 (`schema_version=2`, `built_at=2026-10-28T11:18:41`), а свежий клон вообще не имеет БД и собирает v2 с нуля. Под удар попадает только локальная копия со старой БД v1 — обходной путь один: удалить `memory/corpus.db` и собрать заново.

**Уточнение по цепочке отказа (замер на копии).** `init_schema` пишет `schema_version=2` в meta **до** того, как падает вставка, поэтому после упавшего `build_index` БД остаётся в «полуправом» состоянии: `load_index()` начинает возвращать соединение (схема выглядит валидной), и `index load` на ней падает с `OperationalError: no such column: ord`. **Боевой путь при этом не ломается:** `canon.corpus()` проверяет `is_fresh()` → `False` → читает канон с диска (проверено: `unique=102`, `from_index` не задан, исключения нет). То есть повреждается только управляющий контур (`index build` / `index load` / `index update`), а данные и выдача остаются корректными.
