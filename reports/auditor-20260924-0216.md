## 3. Находки

### №1 [СР] `reset()` обходит FROZEN — заморозка снова беззубая

- **Файл**: `superguard_core.py:244–252`
- **Суть**: цикл 12339 закрыл обход через `evolve()`, но `reset()` по-прежнему безусловно ставит `Status.READY`, `subcycle = 0`. То есть документированное обещание фикса — «`unfreeze()` is the only way back to a working status» (superguard_core.py:130–131) — **не выполняется**: замороженный движок оживает через `reset()`, минуя `unfreeze()`.
- **Репродукция** (реальный вывод независимого теста):

```
FAIL test_freeze_survives_reset: AssertionError: reset() silently unfroze the engine
     -> evolved to EVOLVED subcycle 1
```

  Сценарий: `evolve()` → `freeze()` → `reset()` → `evolve()` — проходит без ошибки; subcycle `1 → 0 → 1`, статус `FROZEN → READY → EVOLVED`.
- **Безопасность последствий**: `reset()` не вызывается **нигде** в проекте (проверено `grep -rn "\.reset(" --include=*.py` по всему дереву, включая `superguard/`, — 0 вызовов; в тестах тоже 0). Значит правка не ломает ни один существующий сценарий, а 64/64 текущих теста от неё не пострадают.
- **Как исправить** (готовый патч, читал файл, строки 244–252):

```python
    def reset(self, force: bool = False) -> None:
        """Reset the engine to initial state ... but keeps the config.

        Cycle 1234x: FROZEN engine refuses reset() (unfreeze()/force=True required).
        """
        with self._lock:
            if self.state.status == Status.FROZEN and not force:
                msg = "Engine is FROZEN. Reset refused; unfreeze() or reset(force=True) required."
                self.logger.warning(msg)
                raise RuntimeError(msg)
            self.state.status = Status.READY
            ...
```

  Вариант без параметра (`raise RuntimeError` всегда при FROZEN) тоже корректен — тогда API остаётся строго однозначным. Аргону выбрать один и добавить тест-близнец к `test_evolve_refused_when_frozen` (`test_freeze_survives_reset`).

### №2 [Н] `save_state()` меняет права файла состояния 0644 → 0600

- **Файл**: `superguard_core.py:364–370`
- **Суть**: `tempfile.mkstemp` создаёт файл с режимом `0600`, и `os.replace` переносит этот режим на целевой файл. Атомарность куплена ценой смены прав: существующий `s.json` с `0644` после первого `save_state` становится `0600`.
- **Репродукция** (реальный вывод):

```
FAIL test_save_state_preserves_file_mode: AssertionError:
     save_state rewrote mode 0644 -> 0o600 (mkstemp 0600)
```

- **Оценка**: на текущей машине всё работает под `thomas`, поэтому severity низкая — [Н]. Но любой внешний читатель (другой пользователь, контейнер, служба под иным uid, синхронизация/бэкап-скрипт) после первой записи теряет доступ к state-файлу; это изменение поведения относительно `open('w')`, которое уважало umask.
- **Как исправить** (в тот же `try`-блок, до `os.replace`; нужен `import stat`):

```python
            try:
                with os.fdopen(fd, "w") as f:
                    json.dump(self.to_dict(), f, indent=2)
                # mkstemp даёт 0600 — сохраняем прежний режим файла (или umask для нового)
                if filepath.exists():
                    os.chmod(tmp_name, stat.S_IMODE(filepath.stat().st_mode))
                else:
                    umask = os.umask(0)
                    os.umask(umask)
                    os.chmod(tmp_name, 0o666 & ~umask)
                os.replace(tmp_name, filepath)
```
