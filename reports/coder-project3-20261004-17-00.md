### Пункт 35 — дифф терял записи с одинаковым ключом (коммит 85550fd) — главная находка слота

**Настоящий баг, а не косметика.** Канонический ключ записи — это тема +
категория + URL, то есть признак дедупликации, а не идентификатор. В
штатном корпусе ключ `unknown|ai engineering|` встречается **дважды** в
цикле 001 и **трижды** в 1351. `diff_cycles()` складывал записи в
`dict[key] = record`, и лишние экземпляры затирались молча: из 102
записей 001 в расчёт попадало 101, из 88 — 86.

Как обнаружил: написал пробу `tools/probe_diff_balance.py`, которая
проверяет два равенства (`removed + moved + shared == from_records` и
`added + moved + shared == to_records`). Оба не сошлись. Ни один
существующий тест этого не ловил — тесты сверяли числа с тем же кодом,
то есть с тем же багом.

Починил: `diff.group_by_key()` (по ключу список, попарное сравнение как
мультимножество), `_is_moved()` принимает итерируемое. Избыток сверх
меньшей кратности идёт в `added`/`removed`, лишние старые экземпляры
проверяются на переезд, а не сразу объявляются пропажей.

Попутно переписал собственный тест: пересчёт был написан через `set(...)`,
то есть повторял ровно тот баг, который обязан был ловить. Заменил на
`Counter` с перебором по объединению ключей.
