### 1. OO-Harness — Object-Oriented Harness (arXiv 2610.28380) — laya 1.6912
`OO-Harness-Object-Oriented-Harness-2026.md` · UIUC + Google Cloud AI Research · полный HTML 97 410 симв. прочитан.
Иерархия **исполняемых классов** харнесса через наследование: evolution agent создаёт подклассы по кластерам
discovery-задач, на инференсе роутер по накопленным **routing lessons** выбирает подкласс или сохраняет базовый результат;
иерархия и уроки замораживаются до деплоя, веса исполнителя — в обеих фазах. Заявленный абсолютный прирост **до 15.79%**.
Три независимых обоснования из литературы, почему глобальный харнесс не годится: Meta-Harness (отбор не переносится при
сдвиге), AHE (эволюционированная память ухудшает простые задачи), EvoHarnessBench (добавление инструментов деградирует
прежнее поведение). Кейс: наследник может **сузить** применимость унаследованного вмешательства; харнесс читает
произведённый артефакт и решает, можно ли завершать.

### 2. SAGE — Social Agent Group Evolution (arXiv 2606.03544) — laya 1.5640
`SAGE-Social-Agent-Group-Evolution-2026.md` · Linyue Pan, Yaoming Zhu · CC BY-NC-SA 4.0.

экспозиции. **Для нас:** наш `journal.md` — это сырые логи; нужен пересказ опыта.

### 4. Optio — триггерная оркестрация кодинг-агентов — laya 1.5295
`Optio-Triggered-Agent-Orchestration-2026.md` · MIT, ★1 078, 27 issues, push 29.10.2026, size 36 313 КБ.
Три яруса: **Tasks** (тикет → merged PR: изолированное окружение, CI, code review, авто-фикс, squash-merge),
**Jobs** (параметризованные прогоны без чекаута), **Agents** (долгоживущие, slug + инбокс + циклическая машина состояний,
`always-on`/`sticky`/`on-demand`, межагентный HTTP API). Ключевое различие: job-model («единица работы = прогон») против
service-model («единица работы = ход»). Control plane — Kubernetes-style reconciliation: чистое «решение + CAS-executor»
с периодическим resync, чтобы прогоны не зависали из-за потерянных событий.

### 5. RiseHarness (arXiv 2610.27435) — laya 1.3862
`RiseHarness-Flipped-Tasks-Handbook-2026.md` · 38 стр., Tencent HY LLM Frontier + Indiana U. + UMD + UGA + NUS.
Flipped tasks (есть и успешные, и провальные прогоны при одной конфигурации) → свидетельства = траектории агента +

### 6. EvoHarness-RL (arXiv 2608.05446) — laya 1.2469 — **ПОСЛЕДНЯЯ 🔴, ЗАКРЫТА**
`EvoHarness-RL-BPE-Harness-Policy-2026.md` · LLA@COLM 2026 · авторы Xuying Ning, Dongqi Fu, Tianxin Wei, Hanqing Zeng,
Yuanchen Bei, Bingxuan Li, Zihao Li, Qifan Wang, Xiang Shen, Yifan Wu, Jiayi Liu, Hong Li, Yinglong Xia, Xiangjun Fan,
Hanghang Tong, Jingrui He.
**Harness policy learning**: агент обучается офлайн политикам харнесса и разворачивает их, чтобы строить и обновлять
внешнее состояние харнесса онлайн. Две связанные проблемы: **формирование состояния** из шумных траекторий и **контроль
доступа** к внешнему состоянию; существующие агенты решают их промптами, эвристиками и ручным проектированием.
**BPE (Belief / Progress / Experience)** — состояние харнесса, на которое пишется политика. Supervised harness
fine-tuning даёт пространство действий харнесса, затем **cost-aware GRPO** решает, **когда** читать, обновлять и
консолидировать. ALFWorld + Qwen3-8B = **96.9% success**.
Две динамики: **harness annealing** — повторяющиеся паттерны использования харнесса интернализуются в политику модели,
агент уходит от частых вызовов харнесса к выборочному доступу; **harness evolution** — обновления прогресса и
консолидация опыта перерабатывают харнесс в **компактную адаптированную подложку**.
**Для нас:** три именованных слота вместо безымянной простыни отчётов; cost-aware чтение/запись (у нас неразличимы по
цене); harness annealing — повторяющийся ритуал слота должен уходить **в инструкцию агента**, а не в очередной скрипт.
