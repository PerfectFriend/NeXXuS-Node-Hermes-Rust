## Таблица по шести критериям

### 1. КРАСОТА — оценка «хорошо»

Сильная сторона слота. Каждый модуль открывается докстрингом, который объясняет
не «что делает», а **зачем существует и какой дефект закрывает**:
`loader.py:1-6` («маркер-скрипт дописывал `# HOT` в начало файлов… для `.json` это ломало файл целиком»),
`chronicle.py:3-6` («ручная вставка ломает хвост файла, а `git add` в монорепо коммитит весь репозиторий»).
Это то, как должна читаться чужая кодовая база без автора рядом.

Дисциплина сообщений об ошибках — предметная часть: `MemoryError_` сообщает путь,
причину и снятые маркеры (`loader.py:52`); валидатор даёт `insights[17]` и конкретное
поле, а не «ошибка в файле». `HOTCODE_NOTES.md` — образец инженерной записки: пять находок
с `файл:строка`, воспроизведением и пометкой «файл только прочитан, правки не вносились».

Минус: не выдержан один формат — пакет не имеет README (`Project1/README*` отсутствует),
пользователь узнаёт о нём только из PLAN.md.

### 2. УДОБСТВО — оценка «хорошо с оговоркой»

Путь до цели короткий и правильный:
`python3 -m p1_memory report` / `validate` / `dedupe` / `chronicle`.
`--json` работает и до, и после имени команды (`cli.py:176-180`) — мелочь, но её обычно
не делают. `dedupe` по умолчанию dry-run, `--fix` обязателен для записи, что исключает
случайную порчу данных.

Оговорки:
- `chronicle` требует от пользователя знать про `--title/--body/--stats`, но нигде в
  проекте нет ни одного примера реального вызова (в CHRONICLE.md запись лежит как
  единственный результат, без строки команды);

### 3. ПОНЯТНОСТЬ — оценка «хорошо»

### 4. БЕЗОПАСНОСТЬ — оценка «не закрыта»

Секретов нет, внешних вызовов нет, subprocess нет, сетевых обращений нет, данных
пользователя не касается — по этим статьям чисто. Но дыра есть, и я её воспроизвёл:

**Находка Б-1. `chronicle --file` пишет вне каталога проекта.**
`cli.py:115`: `path = args.root / args.file`. Абсолютный путь перебивает `root`
(`Path("/proj") / "/tmp/x.md" == "/tmp/x.md"`), `..` тоже проходит:
```
$ python3 -m p1_memory chronicle --title "ПРОБА" --file /tmp/laya_probe.md
Записано в laya_probe.md: ПРОБА
$ python3 -m p1_memory chronicle --title "ПРОБА2" --file ../../laya_probe2.md
Записано в laya_probe2.md: ПРОБА2
```
Утилита вызывается агентами и кронами, `args.root` подставляется из конфигурации —
значит значение `--file` может прийти из чужого источника. Границу нужно держать в коде,
а не в дисциплине вызывающего.

### 5. БЕЗОШИБОЧНОСТЬ — оценка «не закрыта»

**Находка Б-2. Необработанные исключения бьют по краевым случаям, которые сам же код считает своими.**
`cli.py:184` ловит только `MemoryError_`. Всё остальное доходит до пользователя трейсбеком:
```
$ python3 -m p1_memory chronicle --title "   " --file /tmp/x.md
ValueError: заголовок записи пуст        (traceback, chronicle.py:55)
$ python3 -m p1_memory chronicle --title "X" --file /nonexistent_dir_zzz/C.md
FileNotFoundError: ... '/nonexistent_dir_zzz/C.md4_mo_470.tmp'   (traceback)
```
Существование файла и непустой заголовок — контракт самого `chronicle`
(`chronicle.py:54-55`), а не «аварийный» случай: их нарушение гарантировано.

**Находка Б-3. Перевод строки в заголовке ломает структуру журнала и подделывает запись.**
`chronicle.py:32`: `f"### {stamp} — {title.strip()}"` без санитизации.
```
$ python3 -m p1_memory chronicle --title $'ПЛОХОЙ\n### 2020-01-01 — Подделка'
### 2026-10-03 03:27:01 — ПЛОХОЙ
### 2020-01-01 — Подделка
```
Заголовок из CLI или из крона с `\n` превращается в две записи, а худший случай —
в запись, которую `has_entry` примет за настоящую при следующем прогоне. Плюс
`test_repeat_title_is_noop` на этот класс не смотрит.

**Находка Б-4. `total_insights` не сверяется с фактической длиной при загрузке.**
`loader.py:56-58` проверяет лишь «`insights` — список» и досочиняет `total_insights`
по умолчанию. Счётчик, который не сходится с телом, — классический «врёт в тишине»:
`validate_document` его потом находит (`validate.py:90-93`), но только если кто-то
позже догадался вызвать `validate`. Приёмка памяти без него пройдёт.

**Находка Б-5. `.tmp`-мусор при сбое оставляется рядом с данными.**
`tempfile.mkstemp` создаёт `memory/…tmp` до записи; ветка `except BaseException`
(`loader.py:83-85`) чистит tmp, но не уже созданный `.bak`. При падении на
`os.replace` в `memory/` остаётся пара лишних файлов — для каталога, который
перебирается глобом, безвредно, но неаккуратно.

### 6. НАДЁЖНОСТЬ — оценка «хорошо по коду, не закрыта по поставке»

По коду здесь лучше всего: запись атомарна везде (`write-to-tmp + os.fsync + os.replace`,
`loader.py:75-85`, `chronicle.py:74-84`), перед перезаписью делается `shutil.copy2` в `.bak`,
повторная запись идемпотентна, ошибка входного файла даёт exit 2 с понятным текстом,
61 тест зелёные на штатных и на искусственно испорченных данных.

Но поставка не доведена:

**Находка Н-1. Пункты 7–9 отмечены `[x]`, а часть работы не закоммичена.** `git status Project1/`:
```

 M Project1/memory/professor_insights_cycle_1351.json
 M Project1/p1_memory/__pycache__/cli.cpython-314.pyc
?? Project1/CHRONICLE.md.bak
?? Project1/HOTCODE_NOTES.md
?? Project1/MEMORY_REPORT.md
```
Собственное правило плана: «Пункт выполнен только если закоммичен и тесты зелёные».
`HOTCODE_NOTES.md` (пункт 10) и `MEMORY_REPORT.md` (пункт 8) — вне коммита, а это
и есть тот результат, который Продюсер предъявляет как готовый.

**Находка Н-2. Данные памяти изменены вне инструмента и без бэкапа.** В рабочем дереве
с обоих memory-файлов снята строка `# HOT` — единственный diff, и он **не** является
результатом `dedupe --fix`: мусор на месте (102 и 88 инсайтов, 3 мусорных в каждом),
`.bak` рядом нет, `total_insights` совпадает. То есть маркер сняли ручной правкой
в обход `save_atomic`, и на диске это изменение не подтверждено ничем. Для проекта,
чьим главным содержанием является «устойчивость памяти к маркеру», это ровно тот
ход, который система аудита не может отличить от порчи.

**Находка Н-3. `dedupe --fix` на живых данных ни разу не прогонялся.** Атомарная запись
и `.bak` проверены только на временных каталогах. Пункт 7 помечен выполненным, хотя
проверка была «тест на отсутствие `.tmp`-мусора», то есть по своему же критерию — да,
а по живому прогону — нет. Плюс пункт 11 (харнесс на свежем цикле) не выполнен,
и именно он единственный отличает «мусор в накопленной памяти» от «мусор на входе».

**Находка Н-4. В репозиторий попадают `.pyc` и `.bak`.** `git ls-files Project1 | grep -c pycache` → 6.
Корень `.gitignore` (`orchestration/`, `Projects/*/`) ничего этого не покрывает, а сам
`.gitignore` — `??`, то есть не под контролем версий.

**Находка Н-5. Расхождение чисел в отчёте.** `MEMORY_REPORT.md:6` и `PLAN.md:36` пишут
«49 зелёных» тестов; прогон даёт `Ran 61 tests`. Критерий плана для пункта 8 —
«числа в отчёте совпадают с прогоном CLI», и он нарушен. Мелочь в масштабе, но именно
на числах в отчёте дальше строит решение Продюсер.
