## Три AI-агента — подробно

### 1. PentestGPT (USENIX Security 2024)
Академическая работа, 15.7k★, MIT. Агентный конвейер: recon → exploit → walkthrough (CTF) либо
asset discovery → vulnerability identification → report (pentest), находки каждой стадии
питают следующую. Автономный режим **управляет Claude Code или Codex CLI** — то есть не
использует собственный API-клиент, а драйвит уже установленный CLI. Есть персистентность
сессий (сохранить/продолжить). Требует Python 3.12+, `uv`, и авторизованный `claude`/`codex`.
Интерактивный legacy-режим (`pentestgpt-legacy`) поддерживает много провайдеров, включая
локальный Ollama.

**Что взять:** многостадийный конвейер с передачей контекста между стадиями — ровно то, чего
не хватает нашему Живому Коду, где каждый проект живёт в отдельном `PLAN.md`. Плюс практический
приём «агент драйвит установленный CLI» вместо собственного HTTP-клиента — это снимает вопрос
ключей и лимитов.

### 2. HexStrike AI MCP Agents v6.0
MCP-сервер на 150+ security-инструментов и 12+ автономных агентов (BugBounty, CTF Solver, CVE
Intelligence, Exploit Generator и др.). Инструменты сгруппированы: network 25+, web app 40+,
cloud 20+, binary 25+, CTF 20+, OSINT 20+. Есть decision engine (выбор инструмента AI,
оптимизация параметров, discovery цепочек атак), кэширование и восстановление после ошибок.
MIT, принадлежит OTT Cybersecurity LLC (коммерческая организация — проверять условия).

**Что взять:** MCP как шина между агентом и «набором инструментов, которые не хочется
переписывать». У нас сканеры (`ruff`) уже есть, но вызываются вручную. HexStrike — готовый
пример «обернуть существующие CLI в MCP и отдать агенту».

### 3. Strix
66.5k★ — самый популярный в списке, Apache-2.0, активен (пуш за часы до сбора). Ключевое
отличие от классических сканеров: **реальная валидация эксплойтов** — агент пишет и
запускает рабочий PoC, а не рапортует о статическом совпадении. Есть мультиагентная
оркестрация, CLI-ориентированный вывод с рекомендациями по исправлению, автофикс, интеграция с
GitHub Actions (скан каждого PR и блокировка небезопасного кода).

**Что взять:** «находка без воспроизводимого PoC не считается находкой» — тот же принцип, что
мы уже применяем в ревью кода (`interface-review`: «бар для находок — доказательство, а не
вкус»). Стоит взять как правило для нашего eval-контура.

## Классические инструменты — что реально пригодится

- **Gitleaks** (Go, MIT) — 800+ правил секретов, работает по git-истории, есть pre-commit хук.
  Прямая замена нашей самопальной `redact_secrets.py`. Запускается одним бинарником, без

- **Semgrep** (LGPL-2.1) — SAST с «паттернами, похожими на исходный код», 943 открытых issue,
  поддержка C/Go/Java/JS/Python/Ruby. Лёгкий, быстрый, лицензия LGPL (динамическая линковка

- **Nuclei** (Go, MIT) — template-based сканер на YAML-DSL, активно обновляется каждый день.

- **OWASP Amass** — разведка внешней поверхности (домены, поддомены). Актуальность для нас

- **Wazuh / Prowler / Caido** — платформы для развёртывания, не библиотеки. На текущей ноде
  (15 ГБ RAM, из них 10 занято, swap нет) Wazuh не запустится. Prowler полезен только если
  появится реальный облачный аккаунт в scope. Caido — ручной инструмент для реверса трафика,
  к автономному контуру отношения не имеет.

# Приложение A. PentestGPT

**Суть.** Агент, который рассуждает о ходе пентеста и драйвит внешние инструменты. Опубликована
на USENIX Security 2024, отсюда academically-строгий стиль: многостадийный конвейер, а не
«чат-бот с подсказками».

**Состояние на 2026-10-05.** 15 734★, 2 741 форк, MIT, Python. Создан 2023-02-27, последний
пуш 2026-07-14 (три месяца назад — проект жив, но не в горячей разработке). 87 открытых issue.

**Архитектура (v1.0 agentic upgrade).**
- **Стадии с передачей контекста**: CTF — recon → exploit → walkthrough; pentest — asset
  discovery → vulnerability identification → report. Находки каждой стадии питают следующую.
- **Автономный режим управляет Claude Code или Codex CLI** — не собственным HTTP-клиентом.
- **Персистентность сессий** — сохранить и продолжить.
- **Backend-pluggable**: автономный CTF-конвейер работает с Claude Code и Codex; legacy-интерактив
  (`pentestgpt-legacy`) поддерживает OpenAI, Anthropic, Gemini, DeepSeek, xAI, Qwen, Moonshot и
  локальный **Ollama**.

**Требования.** Python 3.12+, `uv`, авторизованный `claude` или `codex` CLI. Есть Makefile
(`make install` → `uv sync`) и Docker-флоу, включающий оба CLI.

**Что берём в Живой Код.**
1. Многостадийный конвейер с явной передачей находок между стадиями. У нас каждый проект
   изолирован в своём `PLAN.md`, и между проектами знание не переходит — это и есть наша
   главная структурная слабость. Конвейер PentestGPT показывает дешёвый способ её закрыть.
2. **Приём «агент драйвит установленный CLI»** вместо собственного API-клиента: снимает вопрос
   ключей, лимитов и форматов ответов. У нас уже есть `living_code_agent_wrapper.py` — та же
   идея, но этот пример показывает, как довести её до произвольного CLI.
3. Локальный Ollama в режиме legacy — релевантно, потому что в профиле Hermes 64k-контекстный
   потолок, и большая часть нашей работы идёт через внешние модули.

**Что не берём.** Требование авторизованного Claude Code/Codex CLI дублирует то, что у нас
уже есть; собственный UI агента не нужен. Код не копируем — идея переносится.

# Приложение B. HexStrike AI MCP Agents

**Суть.** MCP-сервер, который даёт AI-агенту (Claude, GPT, Copilot) возможность автономно
запускать 150+ инструментов безопасности. Не «ещё один агент», а **шина**: слой, превращающий
набор готовых CLI в инструменты одного агента.

**Состояние на 2026-10-05.** 12 386★, 2 521 форк, MIT, Python. Создан 2025-07-10, последний
пуш 2026-08-03. 114 открытых issue. Принадлежит **OTT Cybersecurity LLC** — коммерческая
организация, условия MIT стоит проверить перед использованием в коммерческом коде.

**Архитектура v6.0.**
- **12+ автономных агентов**: BugBounty, CTF Solver, CVE Intelligence, Exploit Generator и др.
- **Decision engine**: выбор инструмента AI, оптимизация параметров, discovery цепочек атак.
- **150+ инструментов**, сгруппированных по домену: network 25+, web app 40+, cloud 20+,
  binary 25+, CTF 20+, OSINT 20+.
- **Process management**: умный кэш, оптимизация ресурсов, восстановление после ошибок.
- Визуальный слой: real-time дашборды, прогресс, карточки уязвимостей.
- Python 3.8+.

**Что берём в Живой Код — главное.**
Это готовый ответ на вопрос «как подключить к агенту инструменты, которые мы не хотим
переписывать». У нас уже есть внешние утилиты (`ruff`, сканеры, `redact_secrets.py`,
gh, yt-dlp), и они вызываются вручную. HexStrike показывает паттерн: обернуть существующие
CLI-команды в MCP-сервер, описать их схемами — и агент получает их как инструменты. Это
дешевле, чем писать обвязку на каждый инструмент, и масштабируется на всё, что появится
в `~/build/bin`.

**Практическая оговорка.** 150 инструментов безопасности на одной ноде с 15 ГБ RAM — это
много. Реальный интерес представляет не весь набор, а архитектурный слой (MCP + decision
engine + recovery). Ставить целиком не нужно; если возьмём — только ядро.

# Приложение C. Strix

**Суть.** Самый популярный в твите (66.5k★). Автономные агенты пентеста, которые **реально
запускают код** приложения, находят уязвимости и подтверждают их рабочим PoC.

**Состояние на 2026-10-05.** 66 554★, 7 305 форков, Apache-2.0, Python. Создан 2025-08-05,
пуш за часы до сбора (2026-10-05 02:37 UTC) — самый активный проект в списке. 436 открытых
issue. Есть облачный тариф (app.strix.ai) и корпоративный, то есть модель монетизации — не
хобби.

**Ключевые отличия.**
- **Real exploit validation** — работающий PoC вместо false positive'ов, от которых страдают
  классические сканеры. Это главный заявленный аргумент проекта.
- Мультиагентная оркестрация: команды AI-пентестеров, которые масштабируются.
- Developer-first CLI: находки с готовыми рекомендациями по исправлению.
- **Автофикс** и интеграция с GitHub Actions: сканирование каждого PR с блокировкой
  небезопасного кода до попадания в прод.
- Полный набор: recon, эксплуатация, валидация.

**Что берём в Живой Код — принцип, а не код.**
«Находка без воспроизводимого доказательства не считается находкой» — это ровно тот же принцип,
который мы уже независимо записали в `interface-review` («бар для находок — доказательство, а не
вкус») и в правила эволюции Живого Кода. Strix — независимое подтверждение, что принцип
рабочий и что он должен быть сквозным: **детект → воспроизведение → только потом отчёт**.

Практическое следствие для нас: любой новый детектор в нашем контуре (gitleaks, nuclei,
semgrep, проверка UI) должен давать не «сработало правило», а воспроизводимый артефакт —
PoC, скриншот, конкретный `file:line` с доказуемым сбоем. Проверки, которые нельзя
воспроизвести, либо убираются, либо понижаются до гипотез.

**Apache-2.0** — самая permissive-лицензия в списке, можно свободно переиспользовать.

# Приложение D. Gitleaks

**Суть.** Находит ключи API, пароли, токены и другие секреты в git-репозиториях. Go, MIT,
один статический бинарник без зависимостей, есть pre-commit хук и выгрузка отчётов
(SARIF/JSON).

**Состояние на 2026-10-05.** 29 672★, 2 269 форков, создан 2018-01-27, последний пуш
2026-09-30, 493 открытых issue. Активно поддерживается, лицензия чистая.

## Почему это наш приоритет

У нас уже есть `~/.hermes/scripts/redact_secrets.py` — самопальный Python-скрипт. Gitleaks
заменяет его по трём параметрам сразу:

1. **Скорость.** Go-бинарь против Python-скрипта, который гоняется в cron-окружении со
   store-python bootstrap'ом.
2. **Полнота.** 800+ правил против самопального набора; community-контрибьюторы постоянно
   добавляют паттерны новых провайдеров.
3. **История, а не рабочая копия.** Секрет, удалённый из файла, остаётся в коммитах. Gitleaks
   сканирует всю историю — именно то, что нужно для «секрет утёк, а файл давно почистили».

## Реальная находка (проверено в этом сеансе)

В `~/Projects/SuperGuard` файл `ACTUATORS_KEYS.txt` с ключами Tuya и локальными IP был
закоммичен в `b71a961` («Initial commit: SuperGuard project») и удалён только позже —
`801fdd9` («chore: remove ACTUATORS_KEYS.txt with Tuya keys and local IPs»). Сейчас файл
есть в `.gitignore` (строка 103) и не отслеживается, **но секреты остались в истории**.

Это ровно тот случай, который ловит Gitleaks и не ловит grep по рабочему дереву.
Значения ключей не читались и нигде не сохранялись: `git log` по имени файла — это единственное,
что выполнялось.

**Что с этим делать (не сделано, требует решения владельца):**
- проверить репозиторий на публичность и наличие форков/клонирований;
- если приватный и форков нет — риск ниже, но секреты всё равно следует ротировать;
- если репозиторий когда-либо был публичным — ключи Tuya нужно отозвать и перевыпустить.

Это действие для человека, не для автоматики.

## Как применять у нас

1. Поставить бинарник в `~/build/bin` (где уже живёт `ruff`).
2. Прогнать read-only по `LivingCode` и `SuperGuard` — сканирование ничего не меняет, можно
   сделать сразу.
3. Дальше — по бэкапу: заменить/дополнить `redact_secrets.py` вызовом gitleaks в cron, чтобы
   проверка шла на каждом проходе эволюции.
4. Приватные репозитории с историей: `--redact` в выводе, чтобы значения ключей не попадали в
   отчёты и в журнал агентов.

## Gitleaks — ставить

**Почему это наш приоритет №1.** У нас уже есть самопальный `~/.hermes/scripts/redact_secrets.py`.
Gitleaks — его профессиональная замена: Go-бинарь без Python-зависимостей (наш cron-окружение

Gitleaks и находит. Значения ключей не выгружались и в отчёт не попадали.

# Приложение F. План применения в Живом Коде

Три вещи из подборки RodmanAi, которые действительно что-то меняют в нашем контуре, и порядок,
в котором их имеет смысл делать. Всё, что требует записи в репозитории или запуска нового
демона, — **после бэкапа** (пользователь отдельно said бэкап и эволюцию в другой сессии).

## Фаза 0 — сегодня, только чтение (бэкап не нужен)

**Установить gitleaks и прогнать read-only по `LivingCode` и `SuperGuard`.**

- Бинарник в `~/build/bin` (рядом с `ruff`), сканирование ничего не меняет в репозиториях.
- Команда: `gitleaks detect --source <repo> --redact --no-banner` (для истории);
  `gitleaks dir <path>` — для рабочего дерева.
- Результат — отчёт в vault, а не в чат: значения секретов не должны попадать в переписку.

Ожидание по SuperGuard: срабатывание на истории из-за `ACTUATORS_KEYS.txt` (см.
[[Gitleaks-карточка]]). Это подтвердит, что инструмент работает, и даст фактические цифры
для отчёта.

**Статус: не сделано.** В этом сеансе ограничились `git log -- ACTUATORS_KEYS.txt` — этого
хватило, чтобы подтвердить факт, но не чтобы измерить масштаб.

## Фаза 1 — после бэкапа: gitleaks в контур

1. **Заменить `redact_secrets.py` на gitleaks** в том же cron-проходе, что эволюция.
   Наш Python-скрипт остаётся как fallback: иногда нужен кастомный паттерн, которого нет в
   800 правилах.
2. **Отчёты — в `~/LivingCode/agents/journal.md` и в vault**, всегда с `--redact`.
   Правило: значение секрета не появляется ни в отчёте, ни в журнале, ни в group-сообщении.
3. **Pre-commit хук** в репозиториях, которые коммитятся автоматически — чтобы не пришлось
   чистить историю потом.

## Фаза 2 — спорно, но интересно: локальный Nuclei против себя

Только против `127.0.0.1` и собственных сервисов. Это легально, бесплатно и даёт нам то, чего
сейчас нет: **живой пример «агент нашёл уязвимость и подтвердил её»** для eval-контура.

Порядок:
- поднять локальный сервис с намеренно слабым местом;
- прогнать nuclei по localhost;
- записать не «nuclei сработал», а конкретный воспроизводимый запрос-ответ;
- добавить это как eval-кейс в `llm-eval-tracker`.

Границы: таргет — только localhost и наши собственные порты. Никакого сканирования внешних
хостов, никаких чужих доменов.

## Фаза 3 — MCP как шина инструментов (по мотивам HexStrike)

**Идея:** обернуть существующие CLI в MCP-сервер, чтобы агент получал их как инструменты по
схеме, а мы перестали вызывать их руками.

Что уже есть и что можно обернуть первым:
- `ruff` (линтер) — уже стоит;
- `gitleaks` — после Фазы 1;
- `gh` (GitHub API);
- `yt-dlp` — есть, но X-видео лучше через API fxtwitter;
- `redact_secrets.py` как fallback-инструмент.

Ожидаемая выгода: инструмент описывается один раз в схеме, и все агенты получают его
бесплатно; сейчас каждый вызов — это руками написанная строка в промпте.

Осторожность: 150+ инструментов на ноде с 15 ГБ RAM — перебор. Berём только ядро, которое
реально используем.

## Фаза 4 — сквозная PoC-дисциплина (по мотивам Strix)

**Правило, которое стоит записать в наши правила эволюции:** отчёт без воспроизведения —
это гипотеза, а не находка. Каждый детектор обязан давать артефакт, по которому сбой можно
воспроизвести снова.

Как это выглядит по нашим классам:
- находка в коде → `file:line` + падающий тест или конкретный вызов, который это доказывает;
- находка в UI → скриншот/DOM-снимок конкретного состояния + шаг до него;
- находка в инфраструктуре → команда и её вывод;
- метрика в отчёте → скрипт, который её пересчитывает.

Это независимое подтверждение принципа, который мы уже записали в `interface-review`
(«бар для находок — доказательство, а не вкус»). Strix применяет его к пентесту, мы применяем
к UI и к коду — одна и та же дисциплина.

## Что НЕ берём

- **Wazuh** — не запустится на 15 ГБ RAM без swap. Отдельная машина или отказ.
- **Prowler** — нет облачного аккаунта в scope.
- **Caido** — ручной GUI-инструмент, к агентам отношения не имеет; вдобавок репозиторий без
  лицензии и без исходников.
- **OWASP Amass** — свои поддомены знаем, чужие периметры не сканируем.
- **Semgrep** — лицензия LGPL-2.1 (динамическая линковка ок, статическая нет); решение об
  установке принимать отдельно, когда будет понятно, куда идёт его вывод.
- **PentestGPT / HexStrike целиком** — идеи переносим, код не копируем.

## Блокеры и что нужно от пользователя

1. **SuperGuard: ротация ключей Tuya** — секреты в истории git (см. [[Gitleaks-карточка]]).
   Проверка приватности репозитория и решение о ротации — за человеком.
2. **Подтверждение объёма Фазы 3** — какие именно инструменты имеет смысл отдавать агенту.
