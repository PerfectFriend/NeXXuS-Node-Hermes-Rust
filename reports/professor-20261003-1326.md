## Главное по существу

**HarnessDev.** Единица оценки — не ответ агента, а его инфраструктура. Один и
тот же GPT-5: 35,2 % на Terminal-Bench в Terminus 2 против **49,6 %** в Codex
CLI — 14,4 п.п. чистого вклада харнесса при фиксированных весах. Opus 4.8
лидирует (67,8 среднего), и **77,8 % провалов в Data — дефекты харнесса**, а не
слабость модели. Три закона для нас:
- разброс расхода токенов **в 19 раз** без пропорционального качества →
  токены обязаны быть второй осью метрики всегда;
- перенос между исполнителями ограничен (доля дублирующихся запросов у Opus
  Search растёт **10,1 % → 88,2 %** при смене модели) → харнесс версионируется и
  проверяется на фиксированном исполнителе;
- мёртвый код харнесса — норма, а не аномалия: **18/108** компонентов кода ни
  разу не наблюдаются, все — состояние и память; чекпоинтинг есть у одного
  харнесса, и в 26 679 траекториях **нет ни одного события чекпоинта**.
- число self-тестов коррелирует с качеством на **0,13–0,26** (не значимо), число
  вызовов ревизии — **0,57** (p ≤ 0,0005) → считать надо циклы
  чтение-отказ→правка→перепроверка, а не тесты.
- шум одной пары задач **±4,75 п.п.**, объявляемая версия попадает в held-out
  оптимум лишь **2 раза из 9** → выбирать по held-out, а не по лучшему видимому
  баллу.

**Self-Harness.** Три стадии (Weakness Mining → минимальный Proposal →
валидация на held-out), Terminal-Bench 40,5→61,9 / 23,8→38,1 / 42,9→57,1.
Граница авторов, которую удерживаем и мы: **addressability criterion** — не
каждый кластер отказов лечится правкой харнесса, слабо обоснованные паттерны
**отбрасываются, а не чинятся насильно**. Не вся неудача цикла — дефект харнесса.

**rudder.** GDPval при одной и той же модели и reasoning effort: rudder **81,7** ·
Codex CLI 75,7 · Claude Code 75,6 (авторы сами называют это directional
evidence). Главная находка — **открытый замер на собственном артефакте**:
скилл `skill-creator` был девятистрочным плейсхолдером; после восстановления и
замера на своих сценариях — **pass rate 19 % → 100 % (10/10)**, время
121,7 → 90,7 с, **токены 51 087 → 129 807**. Замер эталонный, потому что: две
загрязнённые попытки базовой линии **отброшены и перезапущены в изолированных
каталогах**; прирост честно оплачен токенами; один прогон на сценарий —
направленное сравнение, а не оценка разброса. Два попадания в наш протокол:
авторы **явно отказываются** от автоматического продвижения урока в скилл (путь
принятия должен быть явным), и их история планов показывает, что навыки
`*-maintainer` разрослись до отдельной ветки и потребовали сброса к минимуму —
**навык «как чинить» размножается быстрее знания «что чинить»**.

## Десять выводов в Правила роя

1. Разделять создателя и исполнителя — обязательная дисциплина оценки.
2. Токены — вторая обязательная метрика, всегда (19× и +78 720 — один закон).
3. Хардкод лимитов и правил остановки, привязанных к модели, — дефект.
4. Считать циклы чтение-отказ→правка→перепроверка, а не число тестов.
5. Проверять достижимость от точки входа: мёртвый код харнесса — норма.
6. Называть шум измерения до сравнения и выбирать версию по held-out.
7. Читать рассогласование «заявлено / фактически», а не итоговый балл.
8. Ограничения бенчмарка — проверяемые, не декларативные.
9. Путь «фидбек → артефакт» явный, а не автоматический.
10. Загрязнение базовой линии исключать процедурно.
