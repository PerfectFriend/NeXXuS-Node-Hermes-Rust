## Что менял

Одна задача из PLAN.md — идентификатор узла в `internal/registry/registry.go`.

Было:

```go
h := fmt.Sprintf("%x", struct{ uint32 }{rand.Uint32()})
return "node-" + h[:8]
```

Три дефекта в одной строке: `math/rand` (предсказуем после сидирования),
`pubkey` вообще не участвует, 32 бита против заявленных 128. Плюс `%x` на
структуре даёт ведущую `{`, поэтому `h[:8]` — это `{` плюс 6 hex-символов.

Стало: 16 байт из `crypto/rand`, `SHA-256(pubkey + 0x00 + salt)`, первые
16 байт дайджеста, hex длиной 32 символа после `node-`.
Нулевой байт-разделитель нужен, иначе `(pubkey="ab", salt=c...)` и
`(pubkey="a", salt=bc...)` дают один дайджест — неоднозначная конкатенация.
Ошибка `crypto/rand` вызывает panic: возвращать предсказуемый идентификатор
хуже, чем упасть.

## Тесты

## Находка по ходу: harness врал, а тесты были не виноваты

Первый прогон дал M1–M3 «зелёными при снятой защите». Причина оказалась не в
тестах. В `mut-nodeid-test.sh` копия дерева создавалась в `$W`, а Python-скрипт
мутации запускался как `python3 "$W/mut.py"` без смены каталога. Внутренний
относительный путь `internal/registry/registry.go` резолвился в текущий каталог
вызова, то есть в исходник `$P`. Мутировался оригинал, а `go test` гонялся на
свежей нетронутой копии — отсюда зелёный результат при снятой защите.
M4 «поймался» тоже обманчиво: копия для M4 уже несла накопленную M1.

Правка — мутация обязана идти внутри `$W`, плюс проверка, что мутация
реально изменила копию, иначе прогон считается проваленным. После правки
рабочее дерево остаётся чистым, все четыре мутации пойманы.

Это ровно тот случай, о котором говорит гейт 5: счётчик «PASS=3 FAIL=1»
оказался правдоподобным и неверным.
